# Agent Session 旁录与办公工作状态管理：讨论历程记录

## 1. 起点：真正遇到的问题是什么

最开始的问题来自一个非常具体的使用状态：

在一个 Agent 里同时开了很多 Session。每个 Session 都在处理不同事情，或者同一件事情的不同方向。经过一段时间以后，会出现几个问题：

- 不知道每个 Session 最后做到什么程度。
- 第二天重新打开 Agent 时，已经忘记昨天各个 Session 分别在处理什么。
- 即使 Session 历史还在，也需要重新进入、翻聊天记录，才能恢复上下文。
- Session 数量一多以后，单纯依赖标题、最后一条消息或者聊天时间，很难判断它的真实工作状态。
- 有些 Session 并不是“做完一个完整任务”，而是研究了一轮、形成了一些判断以后停下来，之后可能继续，也可能换方向。

最开始考虑的是社区里有没有成熟的“多 Session 管理”方案。

当时关注到两个方向：

1. Claude Code 官方正在强化 Session 的集中查看、恢复和多 Agent 工作视图。
2. Beads 一类工具把任务状态独立于 Session 保存，强调“任务本身持续存在，Session 只是执行者”。

这两个方向提供了启发，但后续讨论逐渐发现：它们都没有完全对应实际办公工作方式。

---

## 2. 第一轮判断：问题可能不是 Session 太多，而是缺少可恢复的状态

一开始形成的判断是：

> 真正的问题不是“Session 太多”，而是每个 Session 缺少一个可以快速恢复的工作状态。

当时提出过一个比较典型的任务状态结构：

- 做到哪里了
- 得出了什么结论
- 还有什么没完成
- 下一步是什么

并且一度把整体结构理解为：

> 项目 → 任务账本 → Session

也就是说，不再依赖 Session 聊天记录本身，而是在 Session 之外维护一个任务账本。

当时 Beads 被认为比较接近这个方向：任务本身独立存在，Session 可以消失，任务状态仍然保留。

---

## 3. 对 Claude Code 与 Beads 的讨论

### 3.1 Claude Code 的方向

讨论中把 Claude Code 的思路拆成了几个层次：

#### Session

Session 是一次具体工作过程，可以恢复、继续、分叉。

#### Agent View

Agent View 更像所有 Session 的总控台，用来快速查看：

- 哪些 Session 正在工作
- 哪些需要输入
- 哪些已经准备好审阅
- 哪些已经完成
- 哪些失败

这类设计解决的是：

> “现在这些 Session 分别是什么状态？”

它减少了重新打开每个 Session 的必要。

#### Memory

Memory 解决的是跨 Session 保留长期信息，例如：

- 项目约定
- 已经确认的背景
- 技术或工作上的长期知识
- 之前踩过的坑

它与“当前 Session 做到哪里”不是同一个问题。

#### Agent Teams

Agent Teams 更偏向多个 Agent / Session 之间的任务协作和共享工作，但当时认为它不是当前问题的重点。

当时对 Claude Code 的归纳是：

> Agent View 管“当前有哪些 Session 在干什么”，Memory 管“以前知道了什么”，Session 本身负责具体工作过程。

---

### 3.2 Beads 的方向

Beads 的思路更强调：

> 任务不属于 Session。

任务本身独立保存：

- 状态
- 优先级
- 依赖关系
- 当前进展
- 后续工作

Session 只是某一次处理这个任务的执行环境。

因此即使 Session 消失，任务依然存在。

当时一度认为，这很适合长期项目，因为它可以解决：

> 一个项目过了一个月以后，到底还有哪些任务没完成？

---

## 4. 重要转折：办公工作不适合提前维护一长串 Task

后续讨论中出现了一个非常重要的修正。

实际办公工作并不是从头到尾按照固定任务树线性执行。

典型情况更像：

1. 先收到一个事情。
2. 研究一轮。
3. 形成一些判断。
4. 做到某个节点时出现新的想法。
5. 原来预计的后续步骤失效。
6. 工作方向发生变化。
7. 继续研究新的方向。

因此，提前列很多 Task 会产生明显问题：

- 当前规划的 Task 可能很快失效。
- 后续 Task 还没有执行，就已经因为思路变化而变得没有意义。
- Task 列表越积越长，其中很多项目已经不再需要处理。
- 需要额外投入精力维护、删除、重排和解释已经失效的 Task。
- Task 管理本身开始成为额外负担。
- 它会把本来具有探索性、判断性和变化性的办公工作，强行变成一个过度结构化的执行计划。

由此形成了一个新的判断：

> 对办公工作来说，提前维护完整 Task 树不一定是正确抽象。

这个判断成为后续整个思路变化的基础。

---

## 5. 从 Task 转向“工作事件”

随后提出了一个更适合办公工作的理解方式：

> 不把 Session 当成任务，而把 Session 看作一次“工作事件”。

一个 Session 可能只是：

- 为某个问题研究一轮
- 做一次判断
- 比较几个方案
- 写出一个阶段性材料
- 验证某个想法
- 形成新的方向
- 处理到某个节点后暂停

它不一定对应一个完整 Task，也不一定有固定的开始—执行—完成结构。

因此，当时尝试把整体结构改成：

> Project → 当前状态 + 一串 Session 工作记录

而不是：

> Project → Task → Session

---

## 6. 第一版“Session 旁录”概念出现

在这个基础上，开始形成“Session 旁录”的想法。

最初的 Session 旁录主要想回答：

- 这一轮为什么开始
- 这一轮实际做了什么
- 形成了什么结论或决定
- 哪些原来的想法已经失效
- 现在事情停在哪里
- 如果继续，可能从哪里继续
- 有没有需要等待的人、材料或时间节点

这里出现了一个重要原则：

> “下一步”不应该重新变成一长串 Task。

例如，不希望写成：

1. 修改方案
2. 找领导确认
3. 制作表格
4. 下发通知

而更希望写成：

> 当前停在“方案基本形成，尚未确认执行口径”。如果继续，优先根据反馈决定是修改方案，还是直接形成正式材料。

这样做的原因是：

- 保留方向，但不把未来强行固化。
- 允许下一轮工作自然改变思路。
- 避免留下大量已经失效的未完成 Task。

---

## 7. 一度把问题进一步抽象成“项目当前状态”

讨论中曾经继续往上抽象，认为除了 Session 旁录之外，还可以给整个项目维护一个“当前状态”。

例如：

- 当前状态
- 已确认内容
- 已放弃方案
- 当前关注点
- 最近一次工作
- 可能继续方向

这样一个项目在跨多个 Session 后，也可以快速恢复。

当时给出的理解是：

> Session 旁录记录一次工作过程，项目状态记录截至现在的整体情况。

这个方向本身成立，但后来被再次收敛，因为用户指出：

> 当前最先要解决的并不是“一个项目如何跨多个 Session 持续推进”。

这个修正非常重要。

---

## 8. 第二次收敛：当前首先解决“每一个 Session 自己是什么状态”

用户进一步明确了需求。

第一个问题实际上是：

> 我首先想知道每一个 Session 的状态。

这里的重点不是项目，也不是任务，而是每个 Session 本身。

希望每个 Session 都有一块旁录信息，可以快速回答：

### Session 开始时

- 一开始为什么开这个 Session
- 最初想处理什么
- 当时的问题背景是什么

### Session 处理中

- 中间大概做了什么
- 研究过什么
- 形成过哪些判断
- 方向有没有变化

### Session 当前状态

- 最后停在哪里
- 做到什么程度
- 当前还有哪些内容没有完成
- 按当时的思路，本来预计后面还需要处理什么

用户明确希望：

> 每轮结束后，可以自动更新一次当前 Session 的旁录。

因此，Session 旁录逐渐被定义为：

> 对当前 Session 工作状态的持续压缩和展示。

它不是一次性的最终总结，而是随着 Session 工作持续更新。

---

## 9. 第二个问题被单独分离：Session 之间可能有关联

在明确单 Session 旁录之后，又提出了第二个问题：

有时候会存在一个主 Session，因为某个子问题需要更纯净的上下文，于是从主 Session 另外打开子 Session。

这会形成类似：

```text
主 Session
├─ 子 Session A
├─ 子 Session B
└─ 子 Session C
```

此时希望未来可能知道：

- 哪个 Session 从哪个 Session 派生
- 为什么拆出去
- 各个子 Session 当前是什么状态
- 子 Session 有没有形成需要回到主 Session 的结果
- 哪些 Session 已经失去继续存在的意义
- 哪些 Session 仍然和主 Session 保持关联

但是这个问题当时没有继续深入设计。

形成的明确共识是：

> 第一个问题和第二个问题要分开。

当前优先解决：

> 一个 Session 自己应该如何形成旁录状态。

至于 Session 之间的关系，后面再单独讨论。

---

## 10. 单 Session 旁录进一步收敛后的结构

讨论中曾经把 Session 旁录压缩成六个字段：

### 本轮起因

为什么开启这个 Session。

### 主要过程

中间主要处理了什么。

### 形成结果

已经形成了哪些结论、产物或判断。

### 当前停点

最后停在什么位置。

### 尚未处理

按照这一轮原来的思路，还有什么没有完成。

### 可能继续

如果从当前状态继续，最可能往哪里走。

这个结构不是最终定稿，但它已经比较准确地对应用户最初描述的需求。

重要的是：

> 它不是日志逐条累加，而是持续覆盖更新的“当前状态投影”。

也就是说，它更像：

> “截至现在，这个 Session 到底是什么状态？”

而不是：

> “这个 Session 曾经发生过哪些事情的完整流水账？”

---

## 11. 开始从 Agent 架构角度看问题：以 Pi Agent 为例

随后问题发生了进一步变化：

不再只讨论概念，而是问：

> 在现有 Agent 架构里，这种 Session 旁录是不是已经有类似能力？

以 Pi Agent 为例，开始关注：

- Pi 的 Session 是如何保存的
- Pi 是否已经有 Session 摘要
- Pi 的 compaction 是否已经包含想要的信息
- 是否可以直接复用，而不是重新设计一套总结机制

这里形成了一个非常重要的思路：

> 也许“Session 旁录”并不需要单独发明。

因为 Agent 本身为了上下文管理，已经在做压缩、摘要、状态保留。

如果这些现有信息足够，只需要把它们从“模型内部使用的信息”转成“给人看的 Session 状态展示”。

---

## 12. Pi compaction 与 Session 旁录的关系

讨论中注意到 Pi 的 compaction 摘要通常包含类似这些内容：

- Goal
- Progress
- Key Decisions
- Next Steps
- Critical Context

这与希望看到的 Session 旁录非常接近。

因此提出了一个最简单的验证方案：

> 先直接拿 Pi 的 compaction 结果作为 Session 旁录，不重新调用模型，不重新设计总结协议。

然后只验证一个问题：

> 第二天看到 compaction summary，能不能立刻知道这个 Session 为什么开的、干了什么、停在哪、后面还有什么？

如果已经够用，就只需要解决：

- 怎么展示
- 怎么更容易读取
- 什么时候更新

如果不够，再调整格式。

这个阶段的思路明显比前面更收敛：

> 先复用 Agent 已经产生的数据，再判断是否真的需要新机制。

---

## 13. 发现 compaction 本身存在两个限制

同时也明确了两个问题。

### 13.1 compaction 的目标用户是模型，不是人

它的主要目的，是在上下文过长时压缩历史，让模型能够继续工作。

因此它可能存在：

- 信息密度太高
- 表达方式偏机器续上下文
- 对“人快速扫一眼”未必最友好

### 13.2 compaction 并不是每一轮都更新

它通常在上下文达到一定程度、需要压缩时才触发。

因此：

> 短 Session 可能根本没有 compaction。

同时，即使有 compaction，它也不一定代表 Session 此刻最新的状态。

所以当时的判断是：

> compaction 很适合作为第一版验证，但它未必天然等于“实时 Session 旁录”。

---

## 14. 从 Pi 转向实际使用环境：OpenHanako

随后用户明确：

> 实际使用的不是直接的 Pi Agent，而是 OpenHanako。

并认为 OpenHanako 是基于 Pi SDK / Pi 体系构建的。

于是问题进一步具体化为：

> OpenHanako 里面，Pi / Agent 已经生成的 compaction 能不能直接提取出来看？

这时思路已经非常清楚：

不是重新设计“怎样让模型总结 Session”，而是优先查看：

> OpenHanako 当前已经保存了哪些 Session 摘要数据。

---

## 15. 对 OpenHanako 的初步判断

前面的讨论中形成了以下方向性判断。

### 15.1 Session 历史和 compaction 很可能已经被持久化

如果 OpenHanako 直接复用了 Pi 的 Session / compaction 机制，那么 Session 存储里应该能够找到 compaction 相关记录。

因此理论上可以：

> 读取当前 Session 最近一次 compaction 的 summary，然后直接展示在 Session 列表旁边。

这会是最低成本的第一版方案。

例如：

```text
合同流程讨论

Goal
完善宣传合同执行流程

Progress
已经确定审批表、工单和变更流程……

Next Steps
继续研究如何转成 Agent Skill……
```

这种展示已经很接近用户最初想要的“旁录”。

### 15.2 OpenHanako 可能还有 rolling summary 一类机制

前面的搜索和讨论中还提到：

OpenHanako 可能存在自己的 rolling summary / memory ticker / context summarizer 机制。

如果这个机制确实持续更新 Session 摘要，它可能比 compaction 更适合旁录，因为：

- compaction 只在上下文压缩时触发
- rolling summary 更可能随着 Session 推进持续更新
- 用户真正想要的是“当前状态”，而不是“上一次压缩时的状态”

因此当时形成了新的研究重点：

> 不要急着开发，先把 OpenHanako 现有 rolling summary 到底什么时候生成、存在哪里、内容是什么搞清楚。

## 16. 当前最重要的思想变化

从整个讨论历程来看，思路发生了几次明显变化。

### 第一阶段

想解决：

> 多 Session 太多，怎么管理？

### 第二阶段

转向：

> Session 太多不是问题，问题是状态不可见。

### 第三阶段

一度采用：

> 项目 → Task → Session

### 第四阶段

发现办公工作不适合稳定 Task 树，因此转向：

> Session 是一次工作事件，不一定是一个 Task。

### 第五阶段

一度考虑：

> 项目状态 + Session 工作记录

### 第六阶段

再次收敛：

> 当前先不要解决项目层，只解决“每一个 Session 自己是什么状态”。

### 第七阶段

进一步收敛：

> Session 旁录不一定需要重新生成，Agent 本身的 compaction / rolling summary 可能已经完成了大部分工作。

因此，目前最准确的问题已经变成：

> 如何把 Agent 已经产生的 Session 状态压缩信息，变成一个长期可见、自动更新、面向人的 Session 旁录展示？

---

## 17. 当前对“Session 旁录”的定义

截至本轮讨论，Session 旁录可以暂时定义为：

> 每个 Session 的伴生状态信息。它随着 Session 工作过程持续更新，用于在不重新进入聊天记录的情况下，快速判断该 Session 从哪里开始、经历了什么、目前停在哪里，以及按照当前上下文还有哪些未完成或可能继续的方向。

它具有几个明确特征。

### 17.1 它属于 Session

不是项目总账，不是全局任务系统。

### 17.2 它不是完整聊天摘要

不要求把整个对话压缩成文章。

只需要保留恢复工作所需的信息。

### 17.3 它不是 Task List

不需要提前规划完整未来步骤。

“未完成”和“可能继续”只是当前状态的一部分，不构成强制执行计划。

### 17.4 它应该持续更新

不是 Session 结束后才生成一次。

理想状态是每一轮重要工作以后刷新。

### 17.5 它最好可以直接展示

目标不是让 Agent 自己读取，而是让人站在 Session 列表层就能快速判断：

- 这个 Session 在干什么
- 做到哪里
- 有没有必要继续打开

---

## 18. 当前候选字段

目前比较接近需求的一版结构是：

```text
本轮起因
最初为什么打开这个 Session。

主要过程
这轮中间主要处理过什么，方向有没有发生明显变化。

形成结果
已经形成的结论、判断、材料、决定或阶段性产物。

当前停点
Session 最后实际停在哪里。

尚未处理
按照这一轮当前思路，还有哪些内容没有处理完。

可能继续
如果继续这个 Session，当前最自然的后续方向是什么。
```

这一结构仍然可以继续压缩。

例如实际 UI 中不一定全部展开，也可以只显示：

```text
起因
当前结果
停点
后续
```

详细信息点开后再看。

目前还没有最终确定字段数量和展示形式。

---

## 19. 与 Task Manager 的明确区别

目前已经可以确定：

这个方向不是在做另一个 Task Manager。

### Task Manager 关注

- 有哪些任务
- 哪些完成
- 哪些未完成
- 谁负责
- 截止时间
- 任务依赖

### Session 旁录关注

- 为什么开这个 Session
- 这轮发生了什么
- 现在做到哪里
- 当前有哪些未结束的东西
- 下一轮如果回来，从哪里恢复

两者最大的区别是：

> Task Manager 试图规划未来，Session 旁录主要记录当前真实发生过的工作状态。

这更适合探索型、判断型、反复变化的办公工作。

---

## 20. 与 Memory 的区别

Memory 也不是这个问题。

Memory 更适合保存：

- 长期事实
- 用户偏好
- 项目稳定规则
- 以后多个 Session 都可能需要的信息

Session 旁录保存的是：

- 当前 Session 的过程状态
- 这一轮工作到哪里
- 这一轮还有什么未完成
- 这一轮下一次如何恢复

因此可以理解为：

```text
Memory
回答：长期应该记住什么？

Session 旁录
回答：这个 Session 现在是什么状态？
```

---

## 21. 与 compaction 的关系

目前的判断不是：

> Session 旁录 = compaction

而是：

> compaction 可能是 Session 旁录最值得优先复用的数据源。

compaction 的优势：

- Agent 已经生成
- 不需要重复调用模型
- 已经包含 Goal、Progress、Decisions、Next Steps 等关键内容
- 本身就是为了压缩 Session 上下文

compaction 的不足：

- 不一定每个 Session 都有
- 不是每轮更新
- 格式主要面向模型
- 最新状态可能晚于最后一次 compaction

所以更准确的关系是：

```text
Session 原始历史
        ↓
Agent 内部状态压缩
   ┌──────────────┐
   │ compaction   │
   │ rolling      │
   │ summary      │
   └──────────────┘
        ↓
面向人的 Session 旁录展示
```

当前最希望验证的是：

> OpenHanako 已经有哪些内部摘要，可以直接作为这层数据源。

---

## 22. 第二个问题：Session 关系，当前暂不展开

除了单 Session 旁录，还有一个已经识别但暂未解决的问题：

> Session 之间的关系。

例如：

```text
主 Session
├─ 子 Session：单独研究一个问题
├─ 子 Session：生成一份材料
└─ 子 Session：验证一个新思路
```

未来可能需要表达：

- parent / child
- 派生原因
- 子 Session 状态
- 子 Session 的结果是否已经回传
- 子 Session 是否仍然活跃
- 是否还有继续存在的必要

但目前明确不把这个问题混入第一阶段。

当前顺序仍然是：

1. 先把单 Session 状态旁录做好。
2. 再讨论 Session 之间的关系。

---

## 23. 当前最值得验证的三个问题

经过前面的不断收敛，现在已经没有必要继续扩展概念。

只需要验证三个很具体的问题。

### 问题一：OpenHanako 的 compaction 是否可以直接读取

需要确认：

- Session 数据中是否保存 compaction
- 保存位置在哪里
- 一条 compaction 的完整字段是什么
- 是否能对应到具体 Session
- 能不能直接取得“最近一次 compaction”

如果可以，第一版 Session 旁录几乎不需要重新生成。

### 问题二：OpenHanako 是否已经有 rolling summary

需要确认：

- 是否真的存在
- 什么条件触发
- 更新频率
- 保存在哪里
- 是否每个 Session 都有
- 内容结构是什么
- 它是否比 compaction 更接近“当前实时状态”

### 问题三：现有摘要是否已经满足人类快速恢复

最终判断标准不是技术实现，而是：

> 第二天打开 Session 列表时，只看这份摘要，是否能在几十秒内知道这个 Session 一开始干什么、中间做过什么、现在停在哪里，以及如果继续大概从哪里开始。

如果答案是“基本可以”，就没有必要重新设计一套复杂的状态系统。

---

## 24. 当前阶段不应该做的事情

根据整个讨论，现阶段有几件事情可以明确暂缓。

### 不要重新引入复杂 Task 系统

因为这会重新回到已经发现不适合办公工作的问题。

### 不要先设计完整项目管理体系

当前问题首先是单 Session 状态，不要提前扩展到项目、任务、多人协作等层级。

### 不要先设计 Session 关系图

主 Session / 子 Session 的关联很重要，但属于第二个问题。

### 不要先开发新的总结模型调用

在确认 Pi / OpenHanako 已经有哪些 compaction、rolling summary 之前，不应该重复生成同类数据。

### 不要追求完整流水账

旁录的目标是快速恢复，不是完整记录所有聊天内容。

---

## 25. 当前最简洁的目标表述

经过前面的多轮修正，现在可以把第一个问题压缩成一句话：

> 给每一个 Agent Session 自动维护一份面向人的“当前工作状态旁录”，让我不进入原聊天记录，就能知道这个 Session 为什么开始、主要做过什么、现在停在哪里，以及按当前思路还有什么没完成或可能继续。

如果进一步结合 Pi / OpenHanako，可以再具体一点：

> 优先复用 Agent 已经生成的 compaction 或 rolling summary，把内部上下文压缩结果直接转成可见的 Session 状态，而不是重新建设一套 Task 管理或总结系统。

---

## 26. 到目前为止的判断

目前已经形成的比较稳定的判断有：

1. **问题不是 Session 数量本身，而是 Session 状态不可见。**
2. **办公工作不适合强制拆成稳定、长期有效的 Task 树。**
3. **Session 更适合被理解为一次工作事件。**
4. **当前首先解决单 Session 旁录，不同时解决项目管理。**
5. **Session 旁录应该描述真实发生的状态，而不是规划一长串未来任务。**
6. **它需要持续更新，而不是只在 Session 完结时总结。**
7. **Pi 的 compaction 已经非常接近所需信息结构。**
8. **如果 OpenHanako 已经存在 rolling summary，它可能比 compaction 更适合作为实时状态来源。**
9. **当前最省事的路线不是重新生成，而是先提取现有摘要。**
10. **第二阶段再处理主 Session / 子 Session 之间的关联关系。**

---

## 27. 尚未确认的内容

以下内容在前面的讨论中被提到，但在真正落地前仍应该以 OpenHanako 当前版本源码和实际 Session 数据为准：

- OpenHanako 当前版本是否完整复用 Pi 的 compaction 存储格式。
- compaction 在 OpenHanako 中具体保存在哪里。
- 当前版本是否稳定存在 rolling summary / memory ticker。
- rolling summary 是否每个 Session 都生成。
- rolling summary 与 compaction 的优先关系。
- 摘要数据是否已经暴露在现有 UI 或内部接口中。
- 是否能够做到每轮工作后自动刷新。
- Session 列表是否容易加入旁录展示。

这些都属于下一阶段的事实核验，不应该在当前概念设计中假定为已经完成。

---

## 28. 目前讨论停点

本轮讨论已经把第一个问题从一个很宽泛的“Agent 多 Session 怎么管理”，逐步收敛到了非常具体的位置：

> 先研究 OpenHanako 现有 Session 数据里已经生成了什么摘要，特别是 compaction 和可能存在的 rolling summary；如果内容已经足够，就直接把它变成 Session 旁录展示。

因此下一步真正值得做的不是继续发散产品设计，而是检查 OpenHanako 当前版本：

1. Session 文件结构。
2. compaction 记录。
3. rolling summary 相关实现。
4. 哪一种摘要最接近“人类可快速恢复 Session 状态”。

到这里，第一阶段的思路已经基本收敛。
